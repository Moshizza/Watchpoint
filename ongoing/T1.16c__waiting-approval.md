Fix implemented (DeviceMap.Ready/MarkReady/BecameReady + ObservationSink defer/replay, no public
contract change) and pushed. Added IRT-U-067…069 directly on ObservationSink+DeviceMap (new
`SinkWithEmptyMap` test helper, mirroring the existing `Sink` helper's pattern). Caught and fixed

often, ~1/15 vs ~8/10 before this fix). Added a `_deferredDrainedWaiters` list so `FlushAsync`
waits for any pending deferred reports to resolve before computing its result. Re-verifying with
repeated runs now; will update the PR checklist and this file to `waiting-approval` once green.

### 2026-11-27T20:05Z claude-pavo — waiting-approval
The `_deferredDrainedWaiters`/`FlushAsync`-waits-for-deferred approach above was wrong and
**reverted**: `FlushAsync` is called from connector code (`PollingLoop`, `SimulatorConnector`,
`MqttConnector`, `ModbusConnector`); blocking it on this connection's own reconcile/map-rebuild is
exactly the cross-call dependency IRT's state machine is built to avoid. Confirmed empirically —
once IRT-U-067 exercised the deferred path without ever calling `MarkReady()`, that version of
`FlushAsync` hung indefinitely (reproduced deterministically, not a timing flake). Root cause of
the IRT-U-048 flake was actually in the test: it reported right after `Connected`, before the
race window even closed, so a genuinely-unknown report could still be deferred when `FlushAsync`
took its snapshot — `FlushAsync` never waited for anything not yet enqueued, deferred or
immediately-unknown alike, and still doesn't after the revert. Fixed by waiting for
`DeviceMap.Ready` before IRT-U-048's `Report*` calls instead.
